# Next의 app 라우팅

파일 시스템 기반 라우팅

Next.js 13버전부터 app 디렉터리 내부의 폴더명이 라우팅이 됨 폴더에 포함될 수 있는 예악어 파일명은 제한되어 있는데

### layout

-   페이지의 기본적인 레이아웃을 구성하는 요소
-   해당 폴더에 layout이 있다면 그 하위 폴더 및 주소에도 영향을 미침
-   root에는 하나의 layout만 가능
    -   모든 페이지에 영향을 미치는 공통 레이아웃(htl, head 등을 다루는 곳)
-   layout은 해당 주소 하위에만 적용이 됨
    -   주소별 공통 UI를 구성할 수 있음

Layout.tsx 예시

```tsx
interface ILayoutProps {
    readonly children: ReactNode;
}

export default function Layout({ children }: Readonly<ILayoutProps>) {
    const diaryMock = diaryViewMock;
    return (
        <div className={S.container}>
            <DiaryView mode="feature" {...diaryMock} />
            {children}
        </div>
    );
}
```

### page

-   기본적으로 제공해주는 props를 받을 수 있음
    -   `params` : 옵셔널 값, [...id]와 같은 동적 라우트 파라미터를 사용할 경우 파라미터에 값이 들어옴
    -   `searchParams` : URLSearchParams를 가져올 수 있음

### searchParams

`layout.tsx`에서는 searchParams 사용할 수 없음
-> layout은 페이지 탐색 중에는 리렌더링을 수행하지 않기 때문, 만약 필요하다면 이 layout을 사용하는 `page.tsx`에서 사용할것!

```tsx
export default function Lyout({
    children,
    searchParams, // undefined
}: {
    children: React.ReactNode;
    searchParams?: { [key: string]: string | string[] | undefined };
}) {
    // searchParams는 항상 undefined
    console.log(searchParams); // undefined

    return (
        <div>
            <div>{searchParams?.category}</div> {/* 작동하지 않음 */}
            {children}
        </div>
    );
}
```

### error

-   해당 라우팅 영역에서 사용되는 공통 에러 컴포넌트
    -   라우팅별로 서로 다른 error 페이지를 보여줄 수 있음
-   에러 바운더리는 client에서만 작동하기 때문에 client 컴포넌트여야함
    -   'use client' 써주기
-   `같은` 수준의 layout에서 에러가 발생할 경우에는 적용되지 않고
-   `하위` 컴포넌트 트리에서 발생한 JS 에러만 잡아줌!

### 에러 바운더리?

에러 바운더리는 React의 개념으로, 하위 컴포넌트 트리에서 발생한 JavaScript 에러를 잡아내고 처리하는 React 컴포넌트를 뜻함

### 에러 바운더리를 초기화?

에러 상태를 원래대로 되돌려서 정상적인 컴포넌트를 다시 렌더링하려고 시도하는 것을 뜻함

```tsx
'use client';

export default function Error({ error, reset }: { error: Error & { digest?: string }; reset: () => void }) {
    return (
        <div>
            <h2>문제가 발생했습니다!</h2>
            <p>에러 메시지: {error.message}</p>

            <button
                onClick={() => reset()} // 에러 바운더리를 초기화
            >
                다시 시도
            </button>
        </div>
    );
}
```

### not-found

-   특정 라우팅 하위의 주소를 찾을 수 없는 404 페이지를 렌더링할 때 사용
-   이름에서도 알 수 있듯이 존재하지 않는 경로에 접근했을 때 보여지는 컴포넌트
-   전체 애플리케이션에서 404를 노출하고 싶다면 app/not-found.js를 생성해 사용
-   서버 컴포넌트로 구성하면 됨 (별도 'use client' 지시자 불필요)

```tsx
export default function NotFound() {
    return (
        <>
            <h2>Not Found</h2>
            <p>404</p>
        </>
    );
}
```

### loading

-   React Suspense를 기반으로 해당 컴포넌트가 불러오는 중임을 나타낼 때 사용
-   페이지나 컴포넌트가 로딩되는 동안 보여줄 UI를 정의
-   서버 컴포넌트로도 사용 가능하고, 'use client' 지시자를 사용해 클라이언트에서 렌더링되게 할 수도 있음

```tsx
export default function Loading() {
    return <div>Loading...</div>;
}
```

### route

-   Next.js 13.4.0부터 app 디렉터리에서 API 라우팅 지원이 추가됨(이전 /pages/api와 동일하게 /app/api를 기준으로 디렉터리 라우팅 지원)
    -   파일명 라우팅이 없어지고 대신 route.ts 파일을 사용
    -   중요: route.ts가 존재하는 폴더 내부에는 page.tsx가 존재할 수 없음
    -   두 파일이 공존하면 충돌 에러 발생

### route 함수의 파라미터

-   request: NextRequest 객체 (fetch의 Request를 확장한 Next.js만의 Request)

    -   API 요청과 관련된 cookie, headers 등 포함
    -   nextUrl 같은 주소 객체도 확인 가능

-   context: params만을 가지고 있는 객체

    -   동적 라우팅 파라미터 객체가 포함
    -   Next.js에서 별도 인터페이스를 제공하지 않으므로 주소의 필요에 따라 원하는 형식으로 선언

```tsx
// app/api/users/[id]/route.ts
export async function GET(request: NextRequest, context: { params: { id: string } }) {
    const response = await fetch(`${}/${context.params.id}`);

    const result = await response.json();

    return new Response(JSON.stringify(result), {
        status: 200,
        headers: {
            'content-type': 'application/json',
        },
    });
}

// POST, PUT, DELETE 등 다른 HTTP 메서드도 동일하게 정의 가능
export async function POST(request: NextRequest, context: { params: { id: string } }) {
    const body = await request.json();

    // POST 요청 처리 로직

    return new Response(JSON.stringify({ success: true }), {
        status: 201,
        headers: {
            'content-type': 'application/json',
        },
    });
}
```

# Layout.tsx 사용 경험

### 그 전에 Parallel Route에 대해서

Parallel Routes란?
Parallel Routes는 Next.js App Router에서 제공하는 고급 라우팅 패턴으로, 동일한 레이아웃 내에서 여러 페이지를 동시에 렌더링할 수 있게 해주는 기능임!

```
app/
├── layout.tsx
├── page.tsx
├── @analytics/
│   └── page.tsx
├── @team/
│   └── page.tsx
└── @dashboard/
    └── page.tsx
```

위와 같은 폴더 구조에서

```tsx
// app/layout.tsx
export default function Layout({
    children,
    analytics,
    team,
    dashboard,
}: {
    children: React.ReactNode;
    analytics: React.ReactNode;
    team: React.ReactNode;
    dashboard: React.ReactNode;
}) {
    return (
        <div className="admin-layout">
            <header>{children}</header>
            <main className="dashboard-grid">
                <section className="analytics">{analytics}</section>
                <section className="team">{team}</section>
                <section className="dashboard">{dashboard}</section>
            </main>
        </div>
    );
}
```

이렇게 독립적인 컴포넌트 렌더링 가능

-   @폴더명: 슬롯(slot)을 의미하는 명명 규칙
-   각 슬롯은 독립적으로 로딩, 에러 처리, 라우팅 가능
-   URL 경로에는 영향을 주지 않음 (@analytics가 URL에 나타나지 않음)

![alt text](image.png)

이런 페이지를 구현할 때 어떻게 레이아웃을 구성해야할까요?(두 페이지의 구성은 url에 따라서 달라짐 ex. 아래 화면 : `diary/1`, 위 화면 : `diary/1/feature/mind`)
제가 생각한 방식은

1. 페러랠 라우트 활용하기
   Parallel Routes를 사용하면 같은 레이아웃에서 여러 컴포넌트를 동시에 렌더링할 수 있음

```
app/diary/[id]/
├── layout.tsx
├── page.tsx                    // diary/1
├── @sidebar/
│   ├── default.tsx            // 기본값 (빈 사이드바)
│   └── feature/
│       └── [type]/
│           └── page.tsx       // diary/1/feature/mind (사이드바)
└── feature/
    └── [type]/
        └── page.tsx           // diary/1/feature/mind (메인 콘텐츠)
```

위와 같은 폴더 구조에서

```tsx
// app/diary/[id]/layout.tsx
interface LayoutProps {
    children: React.ReactNode;
    sidebar: React.ReactNode;
    params: { id: string };
}

export default function DiaryLayout({ children, sidebar, params }: LayoutProps) {
    return (
        <div className="diary-container">
            <main className="main-content">{children}</main>
            {sidebar && <aside className="sidebar">{sidebar}</aside>}
        </div>
    );
}
```

하지만 위와 같은 상황에서 url에 따라 레이아웃이 변동되며, 일기의 내용을 우측 사이드바에 전달을 해줘야하는 상황이었습니다.
물론 패러랠 라우트를 사용했을 때 다음과 같은 장점이 있지만

-   각 영역을 독립적으로 개발/관리 가능
-   URL 기반 라우팅으로 각 슬롯별 다른 페이지 가능
-   로딩 상태를 각각 관리 가능
-   에러 처리를 각 슬롯별로 분리 가능

현재 상황에서와 같이 데이터 공유가 복잡해지는(상위 컴포넌트인 layout.tsx는 client 컴포넌트가 될 수 없으니) 상황이 발생한다면, 패러랠 라우트를 활용하는게 오히려 복잡할 것이라고 생각했습니다.

2. `layout.tsx`에서 `{children}`으로 렌더링

```
// 폴더구조
app/diary/[id]/
├── layout.tsx
├── page.tsx                    // diary/1
├── feature/
│   └── [type]/
│       └── page.tsx           // diary/1/feature/mind
└── components/
    ├── DiaryView.tsx
    └── FeatureSidebar.tsx
```

위와 같은 폴더 구조에서

```tsx
export default function DiaryLayout({ children }: { children: React.ReactNode }) {
    return <div className="diary-page">{children}</div>;
}
```

따라서 이런 식의 `layout.tsx`를 구성한 후 {children} 내부에서 조건부로 렌더링 하는 방식을 사용했습니다.

-   URL 기반 조건부 렌더링 챙기기
-   data fetching(커스텀 훅으로 대체하더라도 동일)과 레이아웃 로직이 한 곳에 모이게 됨 -> props drilling 노노

### 결론

-   Parallel Route의 핵심
    -   독립성
        -   독립적 로딩, 에러, 라우팅
        -   한 쪽 에러나 로딩중이어도, 나머지 부분은 정상적으로 작동할 수 있음
    -   성능 최적화
    -   등등..

Next의 app route는 개발자에게 레이아웃을 구성할 때 사용할 수 있는 여러 선택지를 제공했지만, 각 기능의 목적을 정확히 이해하고 적절하게 사용하는게 중요하다고 생각했음!
